1. Резюме (Executive Summary)

Цель — спроектировать процесс разработки микросервиса «Расчет корзины и
скидок»: выбрать СУБД, настроить репозиторий и защиту веток, внедрить
автоматический контроль качества (flake8 + GitHub Actions), проанализировать
legacy-алгоритм расчета скидок и подготовить план code-review.

Достижения: выбрана PostgreSQL (4.60 против 3.60 у MongoDB); настроена модель
ветвления main → develop → feature/*; develop защищена правилом Pull Request;
Quality Gate проверен методом «сломать и починить»; построена диаграмма
деятельности и выявлены code smells; план ревью оформлен в открытом PR.

2.2. Расчет и обоснование выбора

Формула: Оценка = Σ (Вес_критерия × Балл_кандидата)

PostgreSQL:
0.35·5 + 0.20·4 + 0.20·5 + 0.15·5 + 0.10·3
= 1.75 + 0.80 + 1.00 + 0.75 + 0.30 = 4.60

MongoDB:
0.35·3 + 0.20·4 + 0.20·4 + 0.15·3 + 0.10·5
= 1.05 + 0.80 + 0.80 + 0.45 + 0.50 = 3.60

Победитель — PostgreSQL. Для баллов и финансовых транзакций критичны
атомарность и согласованность (максимальный вес 0.35). PostgreSQL дает полные
ACID-гарантии «из коробки», внешние ключи и ограничения целостности, зрелый
SQL для аналитики и отчетности. Преимущество MongoDB в гибкости схемы
(вес всего 0.10) не компенсирует слабость в транзакционной части: многодокументные
транзакции в MongoDB возможны, но сложнее и дороже по производительности.

5. Обратное проектирование и планирование ревью

5.1. Анализ алгоритма

UML Diagram

Выявленные code smells:

	1.	Магические числа (15000, 0.85, 0.90, 0.97, 0.93, 0.70, 500) — смысл и
происхождение неясны, менять приходится в коде.
	2.	Магические строки промокодов "SUMMER", "VIP" и коды уровней 1, 2.
	3.	Нет валидации входов: отрицательная сумма, неизвестный tier,
promos=None, нестроковые промокоды.
	4.	float для денег — накопление ошибок округления; нужен Decimal.
	5.	Смешение типов скидок (фиксированная −500 и процентные) — результат
зависит от порядка промокодов в списке.
	6.	Повторное применение одного промокода возможно (фрод).
	7.	Перезапись переменной price во многих местах — трудно отследить и
тестировать; нет разделения на шаги.
	8.	Цепочки if/elif, не расширяемые без правки функции (нарушение
Open/Closed); лучше таблица правил / Strategy.
	9.	Неочевидное ограничение: пол 70% применяется в конце «молча»;
не документирован порядок скидок; нет докстринга и тестов.
	10.	Нет округления итоговой цены до копеек.

5.2. План code-review

Подход: PR в develop, ревью по чек-листу из измеримых критериев, роли
автор / разработчик / аналитик-QA / модератор.
Открытый PR: https://github.com/kreynohz/lab1-comprehensive--alek/pull/3
(файл docs/review-plan.md).

Ключевые критерии: 0 магических чисел; 100% валидация входов; покрытие
тестами > 80%; 0 ошибок flake8; сложность <= 10.
Эскалация: обсуждение в PR (до 2 итераций) → созвон с модератором →
решение Tech Lead; споры по бизнес-правилам — владельцу продукта.

6. Заключение

Настроенные процессы снижают риск дефектов на нескольких уровнях: защита
develop и CODEOWNERS исключают прямые пуши и непроверенные изменения;
CI с flake8 автоматически блокирует нарушения стиля и очевидные ошибки до
слияния; формальный план ревью с измеримыми критериями делает проверку
расчетов скидок воспроизводимой; обоснованный выбор СУБД (ACID) защищает
целостность финансовых данных.
