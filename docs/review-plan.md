# План code-review модуля `src/discount.py`

## 1. Цели ревью
- **Точность расчетов** — итог корзины соответствует бизнес-правилам;
  нет ошибок округления (деньги — `Decimal`, а не `float`).
- **Защита от фрода** — нельзя получить цену ниже допустимого порога
  (пол 70% от суммы корзины), отрицательную цену, повторное применение
  одного промокода.
- **Корректность применения скидок** — порядок применения детерминирован
  и задокументирован (базовая → промокоды → лояльность → ограничение).

## 2. Измеримые критерии
| # | Критерий | Порог |
|---|----------|-------|
| 1 | Магические числа (0.85, 0.90, 0.97, 0.93, 0.70, 15000, 500) | 0 — все в именованных константах |
| 2 | Валидация входов (`cart_sum >= 0`, допустимый `tier`, `promos` — список строк) | 100% входов проверяется |
| 3 | Покрытие тестами `src/discount.py` | > 80% |
| 4 | Ошибки flake8 | 0 |
| 5 | Цикломатическая сложность функции | <= 10 |
| 6 | Открытые замечания уровня blocker перед merge | 0 |

## 3. Участники и роли
| Роль | Ответственность |
|------|-----------------|
| Автор (Tech Lead) | Подготовка PR, ответы на замечания, правки |
| Ревьюер-1 (разработчик) | Корректность кода, читаемость, тесты |
| Ревьюер-2 (аналитик/QA) | Бизнес-правила, граничные случаи, фрод-сценарии |
| Модератор | Ведет ревью, следит за сроками (ответ в течение 1 рабочего дня) |

## 4. Процесс
1. Автор открывает PR в `develop`; CI (flake8) должен быть зеленым.
2. Ревьюеры проверяют по критериям из раздела 2.
3. Замечания классифицируются: blocker / major / minor.
4. Merge — после аппрува владельца (CODEOWNERS) и закрытия всех blocker.

## 5. Эскалация при спорах
1. Автор и ревьюер обсуждают вопрос в комментариях PR (до 2 итераций).
2. Если согласия нет — модератор выносит вопрос на 15-минутный созвон.
3. Если решение не принято — финальное слово за Tech Lead; решение и
   обоснование фиксируются в комментарии PR.
4. Споры по бизнес-правилам эскалируются владельцу продукта.
